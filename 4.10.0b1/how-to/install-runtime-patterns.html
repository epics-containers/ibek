Install runtime patterns into an image#

A generic IOC image can carry runtime patterns as well as compiled support modules. Every instance of the image then uses the patterns’ entities without vendoring them, and the image’s published ibek.ioc.schema.json includes them. Run ibek pattern install in the image’s Dockerfile, in the developer stage, after the last compiled support module is installed and before the step that builds the image schema (ibek ioc generate-schema):

RUN ibek pattern install \
    ibek-runtime-streamdevice:EdwardsScroll@0.7.3 \
    ibek-runtime-streamdevice:EdwardsNextTurbo@0.7.3

To vendor a pattern into one instance instead, see Vendor runtime support.

References#

Each reference is library:pattern@version: both the library and the version are required, because an image is built from pins and the library names the support folder the pattern’s database files go in. A library name must therefore be a single folder name that does not start with .; it may not be configure, or the name of a folder already under /epics/support other than one an earlier ibek pattern install created for that library. --list FILE reads further references from a file, one per line, with # starting a comment. A pattern is identified by its library and its name together, and may appear only once in a run.

--source fetches every pattern from one library location (a git URL or a local folder) instead of the one its library name resolves to; see Paths and environment for IBEK_PATTERN_LIBRARIES. Each git library is cloned once per version, however many of its patterns are listed. A local folder is used as it stands, without checking out the version, so its version is only a label: the lock records such a pattern as not verified.

Where the files go#

The pattern’s ibek.manifest.yaml selects its files, as for ibek pattern add. Each selected file is installed by its name, where the image’s compiled support modules put theirs:

Pattern file

Installed to

Found by

*.ibek.support.yaml

/epics/ibek-defs

ioc generate-schema, runtime generate2

*.pvi.device.yaml

/epics/pvi-defs

PVI screen generation

*.proto, *.protocol

/epics/support/configure/protocol

the start script, which copies it to the protocol path

*.template, *.db, *.req

/epics/support/<library>/db

msi’s /epics/support/*/db include path, autosave’s req file search

A selected file of any other type is refused. Files are placed by name alone, so a pattern’s support YAML must name its databases (databases[].file) and PVI files (pvi.yaml_path) without a folder; one that names them by a path is refused. The paths follow EPICS_ROOT.

ibek ioc extract-runtime-assets carries all of them into the runtime image: ibek-defs, pvi-defs and support/configure are among its default assets, and support/<library>/db is picked up by its search for modules’ db folders.

What is refused#

Every pattern in a run is fetched and every destination planned before any file is written. If anything below is found, the install fails and writes nothing. (A write that fails part way, on a full disk for example, leaves the files written so far and no lock entry; in a Dockerfile that fails the build step.)

  • a module that a support YAML in /epics/ibek-defs, or an earlier pattern in the run, already defines;

  • a file that already exists at its destination;

  • two patterns, or two files of one pattern, installing the same file;

  • a pattern listed twice, or one already recorded in the image lock;

  • a pattern that selects no files or no *.ibek.support.yaml, or a support YAML that declares no module;

  • a support YAML that names a database or PVI file by a path;

  • a library name that is not a plain folder name, or that names an existing support module’s folder;

  • a .template or .db name already in another module’s db/ folder, or installed from another library in the same run: msi loads the first match on its include path;

  • a .req name already anywhere under /epics/support or in /epics/autosave: autosave keeps a req file already linked in /epics/autosave, and otherwise links the first of a name it finds under support.

The image lock#

What a run installs is recorded in /epics/ibek-defs/runtime-patterns.lock.yaml:

version: 1
libraries:
  ibek-runtime-streamdevice:
    EdwardsScroll:
      version: 0.7.3
      source: github.com/epics-containers/ibek-runtime-streamdevice
      commit: 4f0c1e2...
      verified: true
      modules:
      - EdwardsScroll
      files:
        ibek-defs/EdwardsScroll.ibek.support.yaml: sha256:...
        support/configure/protocol/EdScroll.proto: sha256:...
        support/ibek-runtime-streamdevice/db/EdwardsScroll.template: sha256:...

Patterns are grouped by library. commit is the library commit the version resolved to, and verified is true, when the library was cloned from git at that version. A pattern from a local --source folder has commit: null and verified: false: its files are whatever the folder held. modules lists the modules the pattern’s support YAML defines, so a tool can tell which modules the image provides from patterns. File paths are relative to EPICS_ROOT.

A later ibek pattern install adds its patterns to the lock. The lock is in /epics/ibek-defs, so it reaches the runtime image with the support YAML it describes. Verify the installed files against it, in either stage:

ibek pattern check --image

In an image with no lock it reports no image lock: nothing installed and succeeds.

Instances that also vendor a pattern#

An instance may vendor a pattern its image already installs. Its config/*.ibek.support.yaml is read after /epics/ibek-defs, so its entity models replace the image’s of the same name, and its protocols and templates are found before the image’s. ibek runtime generate2 warns when the instance defines a module the image also defines, naming both files. To use the image’s copy, remove the vendored files and the pattern’s entry from the instance’s runtime-lock.yaml.
